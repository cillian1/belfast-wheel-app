# Development Process Report: Issue #154

## Executive Summary
The Belfast Wheel development process is a highly autonomous, multi-agent system that successfully delivers updates at a rapid pace (~45-50 minutes per update). However, it is currently limited by artificial daily capacity caps, manual "money rule" verification, and coordination friction in the shared `HANDOFF.md` file. By automating evidence collection for money-related changes and moving to a structured planning model, the team can significantly reduce "stalled" time and merge conflicts.

## Findings

### 1. Capacity Bottlenecks (Daily Caps)
The primary hard bottleneck is the daily task cap on RolexG (8/day), Copilot (15/day), and The Gambler (4/day). 
- **Evidence:** RolexG hit its cap on Task #98 today (Oct 22), halting progress on game sound until the next calendar day.
- **Impact:** Critical bug fixes or polish tasks are deferred unnecessarily, even when model credits or runner time is available.

### 2. "Money Rule" Friction and Stalled PRs
Changes to prizes, odds, or the wallet (money-rule PRs) require a manual Banter notice, a fast-sim result (payback before/after), and an independent review.
- **Evidence:** PRs #120, #134, #136, and #138 are currently in draft or blocked. PR #134 is specifically noted as "(payback gate blocked)".
- **Impact:** High-stakes changes stay in "Draft" state for long periods waiting for bots or humans to provide the required evidence.

### 3. Shared State Conflicts (`HANDOFF.md`)
The `HANDOFF.md` file serves as both the roadmap and the live status board.
- **Evidence:** The Update 25 Retro notes that `HANDOFF.md` was edited 25 times in an hour across multiple branches, making it the only file with frequent merge conflicts.
- **Impact:** Bots spend time resolving conflicts in documentation rather than code, and the "NOW" section becomes a moving target.

### 4. PR Retargeting and Branch Misalignment
Copilot's coding agent defaults to opening PRs against `main`, which must then be manually retargeted to the current `update-N` branch.
- **Evidence:** `HANDOFF.md` explicitly lists "Copilot's PRs open against main, so retarget them to update-N" as a manual step.
- **Impact:** Increases manual coordination work for the lead (Cillian) or the coordinator (Claude).

### 5. Duplication and Dropped Work
- **Dropped Work:** Task #78 (Watch "spinning" bug) has been parked and rescheduled multiple times. PR #92 was "closed for good" after stalling.
- **Duplication:** Manual hand-offs occur when caps are hit (e.g., #109 moved from RolexG to Copilot). Claude and Gemini both perform review tasks that could be consolidated.

## Top 5 Concrete Improvements

### 1. Automated Money-Rule Evidence (Fast-Sim CI)
**The Change:** Integrate `tools/sim/run.mjs` into the `ci.yml` or `gemini-review.yml` workflow. If a PR has "money" in the title, the CI should automatically run the simulation and post the payback comparison as a comment.
- **Evidence:** Current manual requirement blocks PRs #120, #134, #136.
- **Owner:** Claude / Gemini

### 2. Structured "NOW" Plan (API-First Planning)
**The Change:** Move the active task list from `HANDOFF.md` to a structured `tracker-plan.json`. Bots should update their status via this JSON file (handled by `tools/status.mjs`), eliminating text-based merge conflicts in the main handoff document.
- **Evidence:** Retro 25 identified `HANDOFF.md` as the main source of merge conflicts.
- **Owner:** Claude

### 3. Automated PR Target Detection
**The Change:** Update the Copilot dispatch or the coding agent's instructions to read the current holding branch from `version.json` or the structured plan, ensuring PRs are opened against `update-N` by default.
- **Evidence:** Manual retargeting is a documented bottleneck in `HANDOFF.md`.
- **Owner:** Copilot

### 4. Cross-Bot Handoff Protocol
**The Change:** Implement a formal "Cap Hand-off" where a bot that hits its limit automatically tags another bot (e.g., `@copilot /go`) to resume the task, rather than waiting for manual rescheduling.
- **Evidence:** Task #109 was manually moved after a cap was hit; Task #98 is currently stalled.
- **Owner:** RolexG / Copilot

### 5. "Stall Alarm" Automation
**The Change:** A GitHub Action that monitors open PRs for lack of activity (e.g., no pushes for 15 minutes). If stalled, it pings the team on Banter (#30) or attempts to unblock by requesting a re-run or a secondary bot review.
- **Evidence:** Retro 25 noted Task #10 waited 25 mins and Task #9 waited 38 mins without progress.
- **Owner:** Claude
