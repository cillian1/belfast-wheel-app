# Design Report: Double-Arrow and Double Bonus Segments

This report analyzes the proposed addition of "double-arrow" segments (moving ±2 levels) and "double bonus" segments to the Belfast Wheel, as suggested by Austin.

## 1. Level-Move Analysis

The core level-progression logic resides in `src/game/ui.js` within the `runMain()` function's nested wheel loop.

### Findings & Potential Breakage
*   **Level 0/1 Floor:** Current "Go back up" (`UP`) logic at level 1 decrements the loop counter `k` to 0, causing the main wheel (`MAIN`) to spin again. However, a "Double Up" (`U2`) from level 1 or 2 would result in a negative `k`.
    *   **File:Line:** `src/game/ui.js:106`
    *   **Impact:** Attempting to access `LAYERS[k]` with a negative index will cause a runtime crash.
    *   **Fix:** Explicitly clamp `k` to a minimum of 0. If `k` reaches 0, the logic should naturally transition back to the main wheel behavior.
*   **Top-Level Skips:** Jumping deeper (e.g., from Level 1 to Level 3) is technically safe as the loop simply increments `k`. The `dive()` animation handles the visual transition.
*   **Banked Bonuses:** The collection of Wilds and Bonuses is performed per-wheel. Jumping levels means skipping the intermediate wheel's collection opportunity. This is consistent with the "faster" movement intent but reduces the total number of chances to reach 3-of-a-kind.
*   **Watch/Replay Mirroring:** The mirroring system in `src/wallet/watch.js` tracks `zoom` and `rot`. A jump in levels will cause a corresponding jump in `zoom`. The interpolation logic in `mirApply` will smoothly transition the zoom, but if the state capture happens mid-jump, it might look slightly jarring to a watcher. The existing `dive` animation (2.6s) is long enough that multiple state updates should capture the transition.

## 2. Double Bonus Segment

Austin proposed a "double bonus" segment. There are two primary implementation options:

### Option A: Two-Point Advancement
The segment counts as 2 ankhs toward the 3-ankh requirement for the Bonus Room.
*   **Consequence:** Significantly increases the probability of entering the Bonus Round. 
*   **Payback:** Directly increases the Return to Player (RTP). Since the current RTP is already high (99.5% per `src/config.json`), this could potentially push the game into a "house loss" state.

### Option B: Instant Bonus Room
Landing on the segment immediately triggers the Bonus Room, skipping further nested spins.
*   **Consequence:** High-impact "jackpot" style event. 
*   **Payback:** Even higher impact on RTP than Option A. It also cuts the run short, which might be less engaging for players who enjoy the nested tension.

### Recommendation
**Simulation Required:** Any change to bonus collection frequency requires a `tools/sim` run. The simulation must verify that the new segment doesn't break the mathematical "edge" defined in `src/config.json`.

## 3. Wedge Distribution

### Replacement vs. Addition
*   **Adding Wedges:** Increases the total count of segments on a wheel (e.g., from 22 to 23). This slightly reduces the landing probability of every other segment, making the wedges narrower on screen.
*   **Replacing Wedges:** Keeps the wheel geometry identical. Replacing "boring" moves (like standard Forward/Back arrows) is preferred for layout consistency on small phone screens (320px).

## 4. Minimal Version Strategy

For the first implementation, I recommend the following:
1.  **New Move Definitions:** Add `D2` (Double Deeper), `U2` (Double Up), and `DB` (Double Bonus) to `MOVE_DEFS` in `src/game/content.js`.
2.  **Logic Update:** Modify `runMain` in `src/game/ui.js` to handle `k` adjustments for these new keys, ensuring `k` is clamped at 0.
3.  **Visuals:** Update `src/game/faces.js` to draw distinct icons for these (e.g., double chevrons for arrows, two ankhs for the double bonus).
4.  **Sim Validation:** Run the fast-sim to adjust the distribution of these new wedges to maintain the desired RTP.
