# PR #152 Review: Host Wallet Safety Fixes

I have completed a fresh, independent review of PR #152 at its current head. While RolexG has added a test and supposedly updated the code, my investigation shows that `host.html` remains unfixed in several critical areas. Specifically, the wallet race condition fix is not present in `host.html`, the PIN is still stored insecurely, and the requested adjustment limits are missing.

## Findings

### 1. Wallet race condition still present in `host.html` (High)
The `db.txn` implementation in `host.html` (lines 111-127) still contains the logic that permanently disables ETag protection for the session if a network error occurs. 
- **Where:** `host.html:114` and `host.html:119`.
- **Why it matters:** If a host's network blips during a payout or adjustment, the app will fall back to unsafe read-then-write for all subsequent transactions in that session. This can lead to lost money if two phones (or a phone and the host) update a balance at the same time.
- **Suggested Fix:** Sync the `txn` function with the improved version in `src/wallet/db.js` which uses `db.tagSeen` to distinguish between a "header refused" error (CORS) and a transient network error.

### 2. Host PIN stored in `sessionStorage` (High)
The PIN hash is still stored in `sessionStorage`, violating the requirement for memory-only storage.
- **Where:** `host.html:192` (`sessionStorage.getItem('host')`) and `host.html:204` (`sessionStorage.setItem('host', h)`).
- **Why it matters:** Storing the hash in `sessionStorage` means the host remains logged in even after a page refresh or if the tab is closed and reopened. Memory-only storage ensures the PIN must be re-entered after any reload, improving security on shared or borrowed phones.
- **Suggested Fix:** Move the PIN hash to a simple variable (e.g., `let authHash = null;`) that is lost on reload.

### 3. Missing €500 adjustment limit and duplicate-submit handling (Medium)
The "±" adjustment tool lacks an upper bound and is susceptible to double-submits.
- **Where:** `host.html:387-404`.
- **Why it matters:** Without an upper bound, a host could accidentally type an extra zero and gift €5000 instead of €500. Without duplicate-submit handling, tapping "Send" twice could double the adjustment.
- **Suggested Fix:** 
    - Add `if (Math.abs(a) > 50000) return toast('Max €500 per adjustment');` in the `onclick` handler.
    - Disable the "Send" button immediately after it is clicked to prevent multiple submissions.

### 4. Test verifies the wrong file
The new test file `tools/test-wallet-txn.mjs` verifies the logic by reading `src/wallet/db.js`. It does not verify the logic in `host.html`.
- **Why it matters:** The PR claims to have verified the fix for `host.html`, but the test only checks a file that was already fixed in a previous PR (#110).

## Payback Analysis
Payback is **unchanged**. The changes (or attempted changes) are strictly in the host page UI and do not affect the game's payout logic or `src/config.json`.

## Verdict
**Verdict: changes needed.** 

The PR does not fulfill the requirements of issue #151 in the target file `host.html`.
